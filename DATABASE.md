# Green Box — Database Design

PostgreSQL via Supabase. Companion to [ARCHITECTURE.md](ARCHITECTURE.md). This is the proposed schema to be implemented in Phase 2 — not yet applied as migrations.

> **Revision note:** this version incorporates a Phase 0 architecture audit (see [DECISIONS.md](DECISIONS.md) D17–D23). The most significant change: order, payment, and loyalty mutations are no longer plain RLS-gated table inserts — they go through trusted `SECURITY DEFINER` functions (§7) so a client can never forge a price or a points balance.

## 0. Conventions

- Every table: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null default now()`, and `updated_at timestamptz not null default now()` (maintained by a shared trigger) unless noted otherwise.
- Bilingual text fields are paired columns: `*_ar` (required) and `*_en` (optional at the DB level). **Rendering rule:** if the active locale is `en` and `*_en` is null, fall back to `*_ar` rather than showing blank content — Arabic is the guaranteed baseline (see [ARCHITECTURE.md](ARCHITECTURE.md) §8).
- Status/type fields use `text` + a `CHECK (... IN (...))` constraint rather than native Postgres `enum` types — easier to extend later without `ALTER TYPE` transaction restrictions.
- Money fields: `numeric(10,2)`, currency implied EGP.
- Computed monetary totals are Postgres **generated columns** where the formula is fixed (e.g., `orders.total`), not application-maintained fields — removes a whole class of "forgot to keep total in sync" bugs.
- Any entity that can be referenced by a historical order (categories, products, delivery zones/areas, time slots, payment methods) is **soft-deleted** via `is_active = false` from the admin UI. Hard `DELETE` is not exposed in the UI for rows with any historical reference; FK constraints default to `ON DELETE RESTRICT` for these to make that failure loud rather than silently nulling out history.

## 1. Entity Overview

```
profiles ──1:1── auth.users
profiles ──1:N── addresses ──N:1── delivery_areas ──N:1── delivery_zones
profiles ──1:1── carts ──1:N── cart_items ──N:1── products
profiles ──1:N── orders ──1:N── order_items ──N:1── products (snapshot, not live join)
orders ──1:N── order_status_history
orders ──N:1── delivery_zones        (kept for admin filtering/reporting)
orders ──N:1── delivery_time_slots
orders ──N:1── subscriptions (nullable — set when an order was generated by a subscription)
orders ──1:N── payments ──N:1── payment_methods     (1:N = payment attempts, not 1:1)
profiles ──1:1── loyalty_accounts ──1:N── loyalty_transactions ──N:1── orders (nullable)
profiles ──1:N── subscriptions ──1:N── subscription_items ──N:1── products

categories ──1:N── products ──1:N── product_images
products ──1:N── box_items (as box) ──N:1── products (as content item, must not itself be a box)

banners                          -- homepage content

```

## 2. Tables

### `profiles`
Extends `auth.users` 1:1.

| column | type | notes |
|---|---|---|
| id | uuid PK | = `auth.users.id` |
| role | text CHECK IN ('customer','admin') default 'customer' | authorization source of truth |
| email | text | **denormalized** from `auth.users.email`, kept in sync by trigger on signup and on email change. Needed because `auth.users` is not directly queryable by the app under RLS; admin "Customers" screens need to list/search by email without privileged schema access |
| full_name | text | |
| phone | text | |
| created_at / updated_at | timestamptz | |

Created via a trigger on `auth.users` insert (`handle_new_user`) so every signup gets a profile row automatically, with `email` copied in at that point and re-synced on `auth.users` email updates.

**Column-level protection:** `REVOKE UPDATE (role) ON public.profiles FROM authenticated;` — a customer's own-row `UPDATE` policy exists for `full_name`/`phone`, but the privilege system itself denies changing `role`, independent of RLS. A `BEFORE UPDATE` trigger is added as a defense-in-depth backstop that rejects any `role` change not performed by an `is_admin()` session, in case a future migration ever re-grants the column.

**Operational note:** there is no self-service "become admin" path anywhere in the system. The first admin account is provisioned manually (directly setting `role = 'admin'` for a specific user via the Supabase SQL editor) as a one-time Phase 2 setup step — tracked in `TODO.md`.

Replaces the earlier design's loose text-matching against `delivery_zones` (flagged in the Phase 0 audit as an ambiguous relationship — see [DECISIONS.md](DECISIONS.md) D17). A zone's fee/rules apply to **one or many** areas without duplicating the zone row.

## 3. Arabic Text Normalization (`normalize_arabic`)

A small immutable SQL function used by `products.search_text_normalized` (and reusable anywhere else Arabic matching is needed): strips Arabic diacritics (tashkeel) and tatweel, and unifies common spelling variants that would otherwise cause identical searches to miss each other — أ/إ/آ → ا, ى → ي, ة → ه. This is what actually makes search "typo-tolerant" for Arabic; `pg_trgm` similarity on raw, un-normalized Arabic text performs poorly because trivial, extremely common spelling variants would be scored as dissimilar.

## 4. Full-Text & Fuzzy Search

- GIN index on `products.search_vector` (built via `to_tsvector('simple', ...)` — deliberately not `'arabic'`/`'english'`, since Postgres has no bundled Arabic stemming dictionary and assuming English stemming for a bilingual field would be wrong).
- GIN trigram (`pg_trgm`) index on `products.search_text_normalized` for typo tolerance and substring matching.
- Ranking blends full-text rank with trigram similarity, scoped to visible products (§2 visibility rule) — implemented in `lib/services/search`, not in raw client queries.

## 5. `order_number` Generation

Generated server-side inside `create_order` (§7) from a Postgres sequence (`orders_number_seq`) combined with a date prefix (e.g., `GB-20260911-000042`) — **not** a client-supplied value and not a naive `now()`-based string, which could collide under concurrent checkouts. The sequence guarantees uniqueness regardless of how many orders are created in the same second.

## 6. Loyalty Timing Rules

Two things were previously unspecified and are now fixed as explicit, documented behavior (not left to be improvised during Phase 8 implementation):

1. **Earning** happens when `update_order_status` transitions an order to `DELIVERED` — never at order creation. An order that is `CANCELLED` before delivery never earns points, so no reversal is needed on that side.
2. **Redemption** is deducted immediately at checkout (inside `create_order`, if the customer chose to redeem points) via a `REDEEMED` transaction. If that order is later `CANCELLED`, `update_order_status` writes a compensating `REVERSED` transaction restoring the redeemed points to the customer's balance.

Both paths keep `loyalty_accounts.points_balance` and the sum of `loyalty_transactions` for that account reconciled at all times — the balance is never mutated except by writing a transaction row in the same operation.

## 7. Trusted Mutation Functions (RLS Boundary for Money & Points)

This is the direct fix for the Phase 0 audit's most serious finding: a plain RLS policy that lets an authenticated user `INSERT` into `orders`/`order_items` cannot stop them from supplying an arbitrary `unit_price`, `subtotal`, or fabricating a `loyalty_transactions` row for themselves. **Therefore `orders`, `order_items`, `payments`, `loyalty_accounts`, and `loyalty_transactions` have no `INSERT`/`UPDATE` grant for the `authenticated` role at all.** All writes go through narrow, purpose-built `SECURITY DEFINER` Postgres functions, each scoped to exactly one task (never a blanket service-role client in application code):

- **`create_order(cart_id, address_id, delivery_time_slot_id, payment_method_id, customer_notes, redeem_points)`** — verifies the cart and address belong to the caller; re-validates the address's `delivery_area_id` resolves to an active zone; recomputes every line's `unit_price`/`line_total` from the *current* `products.price` (ignores anything the client might have cached); computes `subtotal`/`delivery_fee`/`discount_amount`; creates the `orders` + `order_items` + an initial `payments` row (status `PENDING`) atomically; marks the cart `'converted'`; if `redeem_points` is set and loyalty is enabled and the balance/minimum allow it, writes a `REDEEMED` transaction and sets `discount_amount` accordingly. Returns the created order.
- **`update_order_status(order_id, new_status, note)`** — admin-only (checks `is_admin()` internally); validates the transition is legal; writes `orders.status` and an `order_status_history` row in one transaction; on transition to `DELIVERED`, credits loyalty points (`EARNED`) per §6; on transition to `CANCELLED`, reverses any redeemed points (`REVERSED`) per §6.
- **`record_payment_verification(payment_id, status, verified_by, notes)`** — admin-only; updates a `payments` row's verification fields and, when appropriate, `orders.payment_status`.

Admin UI mutations for orders/payments call these same functions rather than raw table `UPDATE`s, so status history and loyalty side-effects can never be forgotten by a one-off dashboard edit.

## 8. Row Level Security Strategy

RLS is **on** for every table. `is_admin()` is a `SECURITY DEFINER` helper reading `profiles.role` for `auth.uid()`, used inside policies instead of repeating a subquery.

- **Public catalog data** — `categories`, `product_images`, `box_items`, `delivery_zones`, `payment_methods`, `banners`: `SELECT` open to `anon`/`authenticated` filtered by that table's own `is_active`; full read + all writes restricted to `is_admin()`.
- **`products`**: `SELECT` open, filtered by the compound visibility rule in §2 (`products.is_available = true AND category.is_active = true` via join), plus `is_admin()` gets unfiltered `SELECT`; all writes `is_admin()` only.
- **`delivery_areas`**: `SELECT` open, filtered to `is_active = true` **and** its parent zone's `is_active = true`; writes `is_admin()` only.
- **Owned data** — `addresses`, `carts`, `cart_items`, `subscriptions`, `subscription_items`: full `SELECT`/`INSERT`/`UPDATE`/`DELETE` where the row's `profile_id = auth.uid()`. `is_admin()` gets **`SELECT` only** on `addresses` and `subscriptions` (needed for order fulfillment / future subscription support visibility) — admin does not edit a customer's address or subscription directly; that stays the customer's own action.
- **`orders`, `order_items`, `order_status_history`, `payments`, `loyalty_accounts`, `loyalty_transactions`**: customer `SELECT` only, scoped to rows they own (directly or via `order_id`/`loyalty_account_id` join back to their `profile_id`). **No `INSERT`/`UPDATE` policy for `authenticated`** — all writes go through §7's functions. `is_admin()` gets full `SELECT` for support/fulfillment; `is_admin()` does not get a blanket `UPDATE` either — status/verification changes go through the same trusted functions so history and loyalty side-effects stay consistent.
- **`profiles`**: self `SELECT`/`UPDATE` (excluding `role`, enforced at the grant level — see §2); `is_admin()` full access.
- **`settings`, `loyalty_settings`**: public `SELECT`; writes `is_admin()` only.

Every policy gets an explicit Phase 2 test: a second test account must fail to read/write another account's addresses, orders, loyalty data, or subscriptions, **and** a direct attempt to `INSERT` a forged-price `order_item` must be rejected by the missing grant (not merely "no policy matched" — verify it's a hard privilege denial).

## 10. Seeding Policy

Seeded at Phase 2 (structural/confirmed data only):
- The 6 confirmed categories.
- The 2 confirmed payment methods, with blank `account_details` for the admin to fill in.
- `loyalty_settings` default row using the confirmed formula.

**Not** seeded: `delivery_zones`, `delivery_areas`, `delivery_time_slots`, any fee/minimum values, `banners`, any product catalog rows — all admin-entered, since the real values are unconfirmed business data (see [DECISIONS.md](DECISIONS.md)).
